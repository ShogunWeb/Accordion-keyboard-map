# LLM-context.txt — Accordion Keyboard Visualizer (Accordion-keyboard-map)

This file summarizes the project to give an LLM quick context before it
starts working on this application. Reviewed against source code on
2026-09-22. Treat the code and configuration as the source of truth;
re-validate this summary when they change.

## 1. Overview

PWA (React + TypeScript + Vite) that displays the right-hand keyboard of a
diatonic/unisonoric accordion as SVG, and highlights the notes of a selected
chord or scale (computed via Tonal.js). Also manages named songs containing
unique chords, each shown on a complete keyboard, with browser-local storage
and direct PDF download. Personal project, configured for GitHub Pages and
licensed under AGPLv3+. Local features may not yet be deployed.

- GitHub repo: https://github.com/ShogunWeb/Accordion-keyboard-map
- Live app: https://shogunweb.github.io/Accordion-keyboard-map/
- Feedback contact: accordion@shogunweb.be (in-app "feedback" form → mailto)
- Commands below assume the repository root (contains `package.json`).
  Discover it with `git rev-parse --show-toplevel`; paths vary by environment.
- At session start, inspect `git status --short --branch` and any applicable
  repository instructions. Preserve existing user changes; do not assume a
  particular branch, clean working tree, or synchronization with the remote.

## 2. Tech stack

- React 19 + TypeScript, build/dev via Vite 7
- Styling uses plain CSS in `src/styles.css`, `src/App.css`, and
  `src/components/Songbook.css`.
  Tailwind CSS 4 is installed and configured via `@tailwindcss/postcss`, but
  the CSS entry point does not import Tailwind or include its directives.
- Tonal.js (`tonal`) for music theory (chords/scales/pitch class)
- Keyboard rendered in pure SVG (no canvas, no graphics library)
- Direct vector PDF export: jsPDF 4 + svg2pdf.js 2, loaded on demand; no backend
- Tests: Vitest + @testing-library/react + jsdom
- Lint: ESLint 9 (flat config) + typescript-eslint
- API docs: Typedoc (`npm run docs`)
- PWA: hand-rolled service worker (no vite-pwa plugin), manifest.webmanifest

## 5. Keyboard data model

```ts
type KeyboardDefinition = { id: string; name: string; rows: KeyboardRow[] };
type KeyboardRow = { offsetY: number; buttons: ButtonLayout[] };
type ButtonLayout = { index: number; push: string; pull: string };
```

- `rows`: ordered **right → left**
- `buttons` within a row: ordered **bottom → top**, `index` starts at 1.
  Array order determines position; `index` is only the displayed number.
- `offsetY`: vertical offset in **half-button units** (0 = aligned, 1 = shifted
  by half a button, 2 = one full button, etc.) — models the typical staggered
  (quincunx) layout of diatonic accordions. Positive offsets move a row upward.
- `push`/`pull`: note on push/pull, e.g. `"C4"`, `"F#"`, `"Bb4"`, or `""` if
  unknown. Store notes using letter names and ASCII accidentals (`#`, `b`);
  French notation is an output format, not a data-entry convention. The
  helpers do not explicitly normalize French input or Unicode accidentals.

To add a keyboard: create `src/data/keyboards/my-keyboard.keyboard.ts` with a
default export of type `KeyboardDefinition`; it's auto-loaded by
`import.meta.glob` in `data/index.ts`, sorted alphabetically by `name` in the
selector. Use a unique, stable `id` (also used in saved preferences).
No need to touch a central file.

## 6. Application logic (App.tsx)

- Main state: selected keyboard, mode (`chord`/`scale`), root note,
  chord/scale type, language (`en`/`fr`), notation (`anglo`/`fr` = Do Re Mi),
  zoom level, legend visibility, side drawer open state (view "selection" or
  "settings"). Additional session state: view (`keyboard`/`songs`), active
  song ID, and draft chord passed from the keyboard to the song editor.
- `getSelectionHighlights(mode, root, type)` in `src/utils/musicUtils.ts`
  calls Tonal.js's `Chord.get()` or `Scale.get()`, normalizes notes to chroma
  (0–11), and builds preferred labels that preserve musical spelling. App
  memoizes its result; Songbook uses the same helper for every chord card.
  The former `applySelection()` callback and highlighting effects were removed.
- `chordTypes` and `rootNotes` also live in `musicUtils.ts`; scale types and
  French scale names remain in App. `formatChordName()` produces compact song
  labels (`Am`, `E7`, `C` for major), using the selected note notation.
- Selection is applied automatically when root, type or mode changes;
  there is no Apply button. `changeMode()` resets the type to `maj`/`major`
  only when the user switches modes; loading saved preferences no longer
  triggers a mode-reset effect that would overwrite the saved type.
- i18n: separate `en`/`fr` dictionaries in `App.tsx` and `Songbook.tsx`
  (no i18n library). PDF headings/legend also have English/French text.
  Language is inferred from the browser when no preferences are saved.
  UI language and note notation remain independent global preferences.
- Persistence: `localStorage` under the `akm-settings` key, with fields
  `keyboardId`, `language`, `notation`, `fundamental`, `type`, `selectionMode`,
  `zoomIndex`, `showLegend`. Check restoration after reload when changing
  initialization or mode handling; App preference restoration is not covered
  by committed integration tests. Songbook persistence is separate (see §8).
- User feedback: text form that opens a `mailto:` link to
  accordion@shogunweb.be.
- "Source code" link to the GitHub repo in the Settings panel.
- Navigation switches between Keyboard and My songs without a router. Settings
  are available in both views; the closed drawer is inert and aria-hidden.
- In chord mode, "Add to a song" opens My songs with the current chord
  preselected. The user still chooses/creates the target song and clicks Add.

## 7. SVG rendering (AccordionKeyboard.tsx)

- Receives `rows`, `highlightNotes` (pitch classes), `highlightLabels`,
  `notation`, `scale`. Does not compute chords or scales, but converts button
  notes with `toPitchClass`, matches highlights, and formats note labels.
  Matching uses numeric chroma (0–11), so enharmonic notes such as Bb and A#
  match regardless of octave. Highlighted labels use the selection's spelling.
- Each button = a circle split into 2 halves (left = push, right = pull),
  colored blue (`#4A90E2`) when push is highlighted, orange (`#F5A623`) when
  pull is highlighted, otherwise white/gray.
- Positioning: columns = rows (right → left), vertical position computed from
  `position = bIdx * buttonSpacingY + (offsetY * buttonSize) / 2`, then
  `y = verticalPadding + (maxPos - position) + buttonRadius` to draw bottom → top.
- `scale` (prop) drives a responsive button size (zoomLevels in App.tsx:
  `[0.7, 0.8, 0.9, 1, 1.2]`).

## 8. Saved songs (Songbook / useSongbook)

Product scope: a sheet of distinct chords used in a song, not a timeline with
repeated chords. Each card shows the entire selected right-hand keyboard,
with all matching push/pull notes highlighted. There is no automatic fingering
selection or reduction to three/four buttons.

```ts
type ChordSpec = { root: string; type: string };
type SongChord = ChordSpec & { id: string };
type Song = {
  id: string;
  title: string;
  keyboardId: string;
  chords: SongChord[];
};
// localStorage["akm-songbook"] = JSON.stringify({ version: 1, songs: Song[] })
```

- `useSongbook()` is mounted in App, so in-memory changes survive navigation
  between views. It exposes songs, storageError, createSong, renameSong,
  setSongKeyboard, addChord, updateChord, removeChord, moveChord, deleteSong,
  importSongs (atomic additive import with fresh local IDs).
- A song remembers its own keyboard ID. Changing the global keyboard does
  not change existing songs; changing a song's keyboard recalculates its cards.
- Chords are stored as root/type plus a stable ID, not SVGs or computed notes.
  Display order is the array order; move actions exchange adjacent entries.
- Duplicate detection compares exact `root` + `type`, on both add and edit.
  Repeated Am is rejected, while A# and Bb spellings remain distinct. Supported
  roots/types come from the shared selectors; new chord types require updating
  those selectors as well as the Songbook quality labels.
- Songbook supports create/select/rename/delete, chord add/edit/remove/reorder,
  and PDF download. Song title edits save on blur (Enter blurs), with a
  100-character UI limit. Song deletion requires an in-app confirmation.
- The hook reads and validates storage synchronously on initialization. Mounting
  alone never writes; mutations save immediately in their action handlers.
- Validation rejects malformed JSON/schema, unsupported versions, invalid or
  duplicate IDs/chords, and currently unknown keyboard IDs. Invalid saved data
  is preserved, loading returns an empty library with an error, and writes are
  disabled for that session. Do not silently discard or overwrite such data.
- `storageError`: `unavailable`, `quota`, `invalid`, or null. Write failures keep
  edits in memory and surface a message; a later mutation retries if initial
  loading allowed writes. An initial read failure disables writes for the session.
- Storage is local to this browser/origin. No account, automatic cross-device
  sync or cross-tab synchronization. Clearing site data removes saved songs.
  JSON exports provide editable backups/transfers; PDF is printable output.

### Song import/export

- `src/utils/songTransfer.ts` provides parseSongFile, serializeSongFile and
  downloadSongFile, without new dependencies. See `docs/dev/song-files.md`.
- Exchange format: `{ format: "accordion-keyboard-map/songs", version: 1,
  songs: [{ title, keyboardId, chords: [{ root, type }] }] }` in UTF-8 JSON.
  Local IDs, UI preferences, computed SVGs and keyboard definitions are omitted.
  Chord spelling/order are preserved. Local storage uses a different envelope;
  raw localStorage dumps are not accepted as exchange files.
- Export this song downloads one song; Export all songs downloads the library.
  Files use `.akm.json`. Import validates the whole file, then shows a preview.
  Unsupported versions, malformed data or duplicate chords are rejected; empty
  chord sheets are allowed. Both serialization/import enforce a 2 MiB limit.
- Unknown keyboard IDs in exchange files are allowed through syntax validation
  but require explicit UI remapping before import. This differs from the local
  storage parser, which still rejects unknown keyboard IDs.
- Confirmed imports add copies in a single update, with fresh song/chord IDs.
  Existing songs remain intact; colliding titles receive `(2)`, `(3)`, etc.
  `importSongs()` revalidates resolved records before changing state/storage.
  Repeated imports add copies rather than merging; cancelling changes nothing.
- Storage failures keep imported data in memory and display the existing error
  message. Song export is also available while working with unsaved memory data.

## 9. Direct PDF export

- `Songbook.tsx` clones all displayed card SVGs and captures their labels before
  dynamically importing `src/utils/exportSongPdf.ts`. Keep this import dynamic
  so jsPDF/svg2pdf do not enter the initial application bundle.
- API: `exportSongPdf({ title, keyboardName, cards: [{ label, svg }], language })`.
  The exporter creates the document entirely in the browser and downloads a
  sanitized filename derived from the song title; nothing is sent to a backend.
- Vector A4 landscape with an automatic single-row layout, up to four full
  keyboards per page. Header height is measured first (including wrapped titles).
  The widest SVG aspect ratio, fitted to the remaining height, determines how
  many columns fit the available width and gaps. Wider keyboards get three,
  two, or one column rather than being shrunk to force four. All current layouts
  fit four per page; SVG viewBox proportions, not screen zoom, drive this choice.
- Layout constants in exportSongPdf.ts: 12 mm margins, 8 mm gaps, maximum four
  columns. Incomplete final rows are centered with the same keyboard scale as
  previous pages; keyboards are never split. Every page includes song title,
  keyboard name, push/pull legend, chord labels, and page number.
- SVG clones use explicit Helvetica and fixed dimensions derived from viewBox;
  responsive screen styles are removed. The screen SVGs are not modified.
- Titles/labels wrap up to two lines and are truncated if needed. Built-in PDF
  fonts cover French accents; unsupported characters in headings become `?`.
- The download button is disabled for an empty song, missing keyboard, or export
  in progress. Failures produce an error message and allow another attempt.
- Reference production build: initial JS ~78 KB gzip, exporter ~153 KB gzip
  (sizes vary with changes). Optional jsPDF chunks may appear in dist without
  being needed by the SVG export path; inspect actual network requests before
  claiming their download cost.
- The PDF module is fetched on first use, then can be cached by the service
  worker. A first export while offline is not guaranteed; verify caching and
  offline export against a production preview, including after an app update.

## 10. PWA / Service Worker / versioning

- `public/sw.js` contains an `__AKM_BUILD_VERSION__` placeholder replaced at
  build time by `scripts/stamp-sw.mjs`. Caching strategy: cache-first for
  assets, cached `index.html` served for any navigation (offline SPA),
  `version.json` always fetched from the network (`cache: "no-store"`).
  Successful fetched assets are cached with `event.waitUntil` so the worker
  stays alive during cache writes. Lazy PDF resources are not in the static
  precache list; they must have been fetched before offline use.
- `src/serviceWorker.ts`: registers the SW (skipped in dev via
  `import.meta.env.DEV`), checks `version.json` at registration, after a short
  delay, and on focus/online/pageshow/visibility events (no periodic interval).
  A waiting SW triggers the "update available" UI in App.tsx. Choosing Update
  calls `activateServiceWorkerUpdate`, posts `SKIP_WAITING` to the waiting SW,
  then reloads on `controllerchange`.
- Build version generated by `scripts/build.mjs` (format `YYYYMMDD-HHMM-RAND`,
  or overridden via the `AKM_BUILD_VERSION` env var), also injected client-side
  via `define: { __AKM_BUILD_VERSION__ }` in `vite.config.ts` → exposed by
  `src/buildInfo.ts` and shown in the Settings panel ("Build n° ...").
- `vite.config.ts` sets `base: "/Accordion-keyboard-map/"` — important for the
  GitHub Pages deployment (subpath). Adjust if deployed elsewhere (OVH, root,
  etc.).
- `manifest.webmanifest`: name "Diatonic Keyboard", `display: standalone`,
  icons 192/512/512-maskable/180.
- Use `npm run build` rather than invoking `vite build` directly, so the
  client, service worker and version.json receive the same version. Edit
  `public/sw.js`, not the generated copy in `dist/`.
- Validate offline/update behavior with `npm run build` and `npm run preview`
  at the configured subpath; development mode does not register a SW.

## 13. Known gaps / tech debt

- `docs/dev/contributing.md` still references the older
  `src/data/keyboards.ts` (single-file) structure — **outdated**, the actual
  code uses `src/data/keyboards/*.keyboard.ts` (one file per keyboard).
- README's structure tree also contains obsolete paths. `architecture.md`
  describes Tailwind directives absent from the CSS and suggests adding
  persistence that already exists. Its normalization guidance and that in
  `data-model.md` are partly aspirational: actual helpers are `toPitchClass`
  and `formatNoteLabel` in `src/utils/noteUtils.ts`, not `utils/notes.ts`.
  Prefer source code/configuration when documentation disagrees.
- No handling of the left-hand (bass) keyboard — noted as a future extension
  in `docs/dev/architecture.md`.
- No routing, single-page app.
- i18n limited to en/fr, hardcoded in the UI components and PDF exporter.
- Removing/renaming a keyboard ID currently makes a saved songbook referring
  to it fail validation. Songbook has a missing-keyboard UI fallback, but the
  parser rejects that state during reload; consider a migration/recovery path
  before changing keyboard IDs.
- Full App interaction/offline validation is still needed (see §12).
- README lists "Import/export of keyboard JSON layouts" as a future
  improvement, not yet implemented.

## 14. Quick start

From the repository root, install dependencies and start development:

```bash
npm ci
npm run dev        # normally http://localhost:5173/Accordion-keyboard-map/
```

Run validation separately (dev is a long-running server):

```bash
npm run lint
npm run build      # TypeScript + production build + version stamping
npm test -- --run  # single run; build artifacts must already exist
```

For changes affecting UI or behavior, also check the relevant scenarios in
a browser:

- Switch layouts and verify row order, staggering and push/pull halves.
- Try chord and scale modes, including sharps/flats and enharmonic notes.
- Change language and note notation independently; check zoom and mobile layout.
- Reload after changing preferences, including a non-default chord/scale type.
- Create a song with Am, Dm, E7; attempt a duplicate add/edit, reorder/remove,
  rename it, change its keyboard, navigate between views, and reload.
- Download landscape PDFs with 1, 2, 3, 4, 5, and 7 chords on different keyboard
  layouts. Check automatic column counts, centered partial final rows, every
  button/note, French accents, long titles, sharp/flat spellings, page breaks,
  and readable print size.
- Check that the PDF module is not fetched on initial load; export once online,
  reload offline, and retry. Also test a first offline export without a cached
  exporter and confirm a useful error rather than a stuck download button.
- Export one/all songs and import into an empty and an existing library; check
  order, keyboard, names, fresh IDs, cancellation and invalid files. Resolve an
  unknown keyboard explicitly and reload to confirm the mapped song persists.
- For PWA changes, use preview to check offline loading after assets are cached,
  then a second build with a new version to check the update prompt and reload.

## 15. Working-session guidance

- Read the relevant source before editing; this file is a starting map.
- Preserve the data conventions in §5, chroma-based matching, and the separate
  language/notation settings when changing musical or display behavior.
- Keep English/French entries in sync in both App and Songbook, and update PDF
  text when relevant. Language and note notation are independent.
- Use the shared music helpers and existing SVG renderer for new chord views.
  Preserve per-song keyboard IDs, stable chord IDs, and duplicate rules.
- Treat stored song data as user content: version schema changes and preserve
  unreadable data. Exchange files are a separate versioned schema; preserve
  additive import semantics and explicit mapping of unknown keyboards.
  Keep PDF dependencies behind the dynamic import.
- Write commit messages in English (also configured for VS Code Copilot in
  `.vscode/settings.json`).
- Treat `dist/` as generated output; change sources and rebuild.
- Report the checks actually run and any remaining validation limits.
- Update this context when architecture, commands, data conventions or PWA
  behavior change. Keep task-specific goals and progress in the session rather
  than recording temporary Git state or machine-specific paths here.
